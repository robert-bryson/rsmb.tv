# Tornado Tracks

Route: `/projects/tornado-tracks/map`

## Features

- Full-screen MapLibre map at `/projects/tornado-tracks/map`
- NOAA/NCEI StormEvents automated sync pipeline (`syncTornadoes.js`)
- Per-year GeoJSON split under `https://data.rsmb.tv/tornadoes/tracks/{year}.geojson`
- Density (heatmap) mode reuses the loaded tracks' start points without another GeoJSON download
- Annual summaries and notable events generated during data sync
- EF-scale filter and region presets: U.S. archive, Midwest, Plains, and Dixie Alley
- Year range timeline with play/pause animation
- Scale, year, and decade color modes
- Trends panel with annual counts, linear regression, deaths per 100 segments, decade comparisons, and state totals
- Warning/watch trends: storm-based NWS warning counts by WFO, SPC watch counts, and approximate StormEvents report-match rates
- WebGL fallback SVG renderer for environments without GPU support
- Filter and camera settings stored in URL parameters
- Share button copies the current URL to the clipboard
- Mobile controls/details panel, with automatic opening on track or state selection

## Data storage

The `rsmbtv-temperature-data` S3 bucket stores tornado data under `tornadoes/`.
The `data.rsmb.tv` CloudFront distribution serves these files and the temperature records.

- By default: `https://data.rsmb.tv/tornadoes/…` (CDN-served)
- For local generated data: set `VITE_TORNADO_DATA_BASE_URL=/data/tornadoes`

Git excludes generated files in `public/data/tornadoes/`.
The `sync-tornadoes.yml` workflow runs the sync, uploads the results, and invalidates CloudFront caches.
The workflow does not commit generated data.

GeoJSON files are served with `Content-Type: application/geo+json` (RFC 7946).
JSON summary files use `Content-Type: application/json`.

```
  types/index.ts            # All TypeScript types
projects/tornado-tracks/
  scripts/
    syncTornadoes.js        # NOAA/NCEI StormEvents sync + GeoJSON generation
public/data/tornadoes/      # gitignored — generated by sync, served from S3/CDN
  tracks/{year}.geojson     # LineString per mappable county segment

  annual-summary.json
  state-summary.json
  notable-events.json
  warning-summary.json     # IEM warning/watch analytics + report-match summaries
```

## Sync pipeline

```bash
# Run from repo root
node projects/tornado-tracks/scripts/syncTornadoes.js
# Or via the top-level backfill script:
node scripts/backfill.js --projects tornadoes
node scripts/backfill.js --projects tornadoes --storage local,s3
```

The sync downloads NOAA/NCEI StormEvents CSV files and normalizes F/EF scale labels.
It excludes rows with invalid coordinates.
It writes yearly GeoJSON and summary JSON to `public/data/tornadoes/` before upload.
It also downloads IEM storm-based warning files from 2002 onward and SPC watch files from 1997 onward.
These files supply `warning-summary.json` for the Trends panel.

The `.cache/tornado-tracks/` directory stores downloaded source files between runs.
NOAA files with versioned names remain cached. IEM warning and watch files expire after six days.
The sync stops before replacing output when a historical source file is missing.
It also stops when a downloaded year has no valid tracks or contains tracks from another year.
An empty complete archive also fails validation.
The writer prepares all output in a sibling staging directory before it replaces the existing archive.
If replacement fails, it restores the previous directory.
If restoration also fails, the error identifies the retained backup directory.
After a process interruption during replacement, check for a sibling `.tornadoes-staged-*.previous` directory before retrying.

In CI (`sync-tornadoes.yml`), output is uploaded to S3 instead of committed.

## Backfill

To populate data from scratch (all years, 1950–present):

```bash
# Write output locally only:
node scripts/backfill.js --projects tornadoes

# Write locally and upload to S3 + invalidate CloudFront:
node scripts/backfill.js --projects tornadoes --storage local,s3 \
  --bucket rsmbtv-temperature-data --cdn-id <DISTRIBUTION_ID>

# Using environment variables (recommended):
TORNADO_DATA_BUCKET=rsmbtv-temperature-data \
TORNADO_DATA_CDN_ID=<DISTRIBUTION_ID> \
  node scripts/backfill.js --projects tornadoes --storage local,s3
```

See `scripts/backfill.js` for full option documentation.

## Trend analytics

The Trends panel (`mode=trends`) uses `annual-summary.json` for unfiltered national comparisons.
State, region, and intensity comparisons load historical tracks.
Warning and watch data load separately when Trends opens. These requests cannot block the map.
The panel contains these views:

- **A · Annual count vs selection** — bar chart with OLS trend line and
  comparison pills (Avg/yr, Deaths/yr, EF2%) for the selected range vs full
  history. The current in-progress year is excluded to avoid skewing downward.
- **B · Counts and deaths per 100** — annual segment counts and deaths per 100 recorded county segments.
- **C · Decade comparison** — horizontal bar chart by decade, toggle between
  Avg/yr, Deaths/yr, EF2+%, and Deaths per 100.
- **D · Top states** — horizontal bar chart of the most affected states in the
  selected year + scale filter window, toggle between Count, EF2+%, and Deaths.
- **E · Warnings and watches** — annual storm-based warning counts, selected
  range totals, top WFOs, SPC watches, and approximate report-match rates.

Multi-year percentages and deaths per 100 segments use summed counts as their denominator.

## Interaction notes

- Map viewport changes write `lat`, `lng`, and `zoom` into the URL. Filter
  updates are composed through a pending URL draft so a scroll or pan `moveend`
  cannot overwrite a just-selected `tracks` / `density` / `trends` mode.
- The share action belongs with the analysis controls: desktop keeps it in the
  right summary panel header; mobile exposes it through Filters & details.
- Mobile starts with a collapsed timeline to preserve map space. The controls
  panel supports Escape to close and returns focus to its trigger.
- Timeline bars expose year/count labels and support left/right arrow navigation.
- One histogram bar remains in the tab order when the selected range starts in a missing year.
- Data failures leave the controls available and provide Retry above the open phone panel.
- Annual metadata must contain unique, supported years and finite, nonnegative metrics.
  The loader sorts valid metadata before charts use it.
  Invalid or empty metadata shows an error and blocks geometry requests. Retry reloads metadata.
- Geometry requests use only years in the published annual summary.
- Historical downloads run at most six year requests at once and stop queuing
  obsolete files when the selection changes. Already active requests can finish
  and warm the shared cache.
- Notable-event navigation clears incompatible geography/intensity filters.
- The `conus` URL/default preset is labelled U.S. archive: it includes offscreen
  Alaska, Hawaii, and Puerto Rico records, while the initial camera covers CONUS.

## Known limitations

- One source row is a recorded county segment, not necessarily one unique tornado.
  See the [NOAA FAQ](https://www.ncdc.noaa.gov/stormevents/faq.jsp). Counts, heatmaps,
  and rate denominators reflect these records; this app does not merge county segments.
- NOAA publication lags the event date by several months. The current year is
  excluded from historical comparison charts and warning/WFO comparisons.
- Tracks are start→end straight lines, not damage-path swaths. DAT survey
  polygons would improve modern events but require a separate data layer.
- EF0 count trends are noisy (reporting practices changed over time). Filtering
  to EF1+ improves trend interpretation.
- WebGL is unavailable in WSL without GPU passthrough; the SVG fallback handles
  this automatically.
- `state-summary.json` is generated and stored in S3 but not yet consumed by
  the frontend (state breakdown is computed client-side from loaded tracks).
- Warning report matching is approximate: warnings are matched to StormEvents by
  WFO/time, while SPC watches use watch bounding boxes and valid time. It is good
  for broad context, not formal warning verification.
